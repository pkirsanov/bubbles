# Design: BUG-037 — Opt-Out User Acceptance

> **Status of this document.** The design was reconciled on 2026-09-01 after
> the gaps phase found contradictions in D-1 and D-5. This revision defines the
> current failure-code lifecycle and legacy migration classes. It changes no
> source, registry, test, generated, acceptance, or certification surface.

---

## 0. Design Brief

**Current state.** The shipped registry implements opt-out acceptance. The
checklist ships checked, unchecked items still block, and the acceptance record
is optional. The library also retains the downstream required-at-terminal
override. Its conditional code is undeclared, registry-read failures can accept,
and the upgrade note collapses two legacy template epochs into one.

**Target state.** Keep opt-out behavior and user rejection authority unchanged.
Declare every supported failure code, fail closed when authority cannot resolve,
and classify legacy files by scaffold provenance. Planning, source, registry,
documentation, and tests must then adopt one contract before certification.

**Patterns to follow.**
- Single-authority-plus-shared-reader, already in place:
  [acceptance-authority.yaml](../../bubbles/registry/acceptance-authority.yaml)
  is data, [acceptance-authority-lib.sh](../../bubbles/scripts/acceptance-authority-lib.sh)
  is the only parser, and both the lint and the guard source it. Change the data
  and the reader; never re-implement the parse at a call site.
- Guard-prints-and-stops, never guard-edits — Check 43's existing posture.
- Generated artifacts are regenerated by their generators, never hand-edited.

**Patterns to avoid.**
- The three-rule composition that PD-12 correctly diagnosed: template ships
  checked *because lint refuses otherwise*, and the terminal gate then reads
  those boxes as sign-off. The checked state must come from the CONTRACT
  (`shippedState: checked`), never from a lint refusal. This is why D-2 declines
  to restore the lint rule.
- Fixing a prose surface by text substitution without re-reading the script it
  describes. That is exactly how the four stale surfaces were produced.
- Treating `[ ]` authored by a template as equivalent to `[ ]` a user typed.
  They are indistinguishable in the file. Separate them through scaffold
  provenance and review history, not bytes or a cutover date alone. See D-1.

**Resolved decisions.** All five are closed in § 3. D-1 classifies legacy files
by their authoring-contract epoch and forbids bulk migration. D-2 keeps lint
shape-only. D-3 assigns initial authoring and later mutation to different
agents. D-4 keeps BUG-032 out of scope. D-5 keeps the `PD12-*` prefix and
classifies `PD12-NO-RECORD` as conditionally active.

**Open questions.** None at the design layer. Eight non-design findings remain
open and are routed in [report.md](report.md#bug037-design-remediation).

## 1. Root cause — CONFIRMED

Confirmed by `bubbles.design` against the files, not from the bug narrative.
The preliminary framing in § 1.1 is upheld, and the narrower alternative it
raised is **resolved in favour of the narrower reading** on new evidence
recorded in § 1.3.

### 1.1 Primary cause — a sound repair applied against an unrecorded requirement

Commit `9e41da4` identified a real fabrication vector: the template shipped
checked, lint *required* it to ship checked, and Gate G136 then read "every item
checked" as terminal human acceptance. Composed, those three rules said that
writing the template constituted the sign-off. That is a genuine defect and
PD-12 was right about it.

The repair chosen was to invert the default: ship unchecked, drop the lint
requirement, and add a separately authored `## Human Acceptance Record` as the
terminal proof. That repair optimises for un-forgeable proof of a human act.

The failure is that it made the owner's **normal case unreachable**. A user who
reviewed the delivered behavior and objects to nothing must now perform two
positive acts before the work can be called done. Nothing in the repository
recorded the owner's opt-out requirement at the time, so no surface contradicted
the change and no guard caught it.

### 1.2 Secondary cause — executable and descriptive surfaces updated on different clocks

`9e41da4` updated the template, the lint and the guard, and left the gate
registry, two shared agent modules, the skills catalog row and the changelog
describing the prior contract. Nothing in the repository forces a gate's
`description` to agree with the script that enforces it, so the drift was
silent.

**Confirmed against the files.** Each of the four reported surfaces still
carries both false assertions at HEAD:

| Surface | Line | Verified stale text |
|---|---|---|
| `agents/bubbles_shared/quality-gates.md` | 272 | "requires the checklist to carry at least ONE checked `[x]`"; "a checked-by-default template is legitimate" |
| `agents/bubbles_shared/test-core.md` | 304, 309 | same two assertions |
| `skills/bubbles-quality-gates-catalog/SKILL.md` | 57 | same two assertions |
| `CHANGELOG.md` | 1320 | the only G136 entry; carries both assertions; no PD-12 entry exists anywhere in the file |

`bubbles/registry/gates.yaml` `G136.description` (line 1074) carries the same
pair. Five surfaces, not four.

**Scope ruling on the mechanical-drift-check question the bug packet raised.**
A general "gate description must agree with its enforcer" check is **out of
scope for BUG-037** and is recorded as a candidate improvement. BUG-037 already
carries four scopes and a contract inversion; adding a new cross-cutting
conformance mechanism would widen it past the defect. What BUG-037 *does* ship
is the narrow version of that check scoped to this gate: S4-T1 (no surface
asserts the deleted lint requirement) and S4-T2 (`G136.description` names only
codes the guard can emit).

### 1.3 The narrower cause is the correct one — new evidence

§ 1.1 asked whether the true fabrication vector was the **lint requirement**
that forced the checked state, rather than the **checked default** itself. Two
surfaces found during the § 2.5 sweep settle it, and both are surfaces
`9e41da4` never touched:

| Surface | Line | Text at HEAD |
|---|---|---|
| `agents/bubbles.plan.agent.md` | 230 | "`uservalidation.md` — Create with checked-by-default baseline template (`- [x]` items)." |
| `docs/guides/FRAMEWORK_CONCEPTS.md` | 59 | "Human acceptance checklist — **users uncheck items to report regressions**" |

`bubbles.plan` OWNS `uservalidation.md` creation, and its instruction has said
"checked by default" continuously since before `9e41da4` and still says it at
HEAD. `FRAMEWORK_CONCEPTS.md` describes the opt-out mechanism explicitly.
Neither was updated by `9e41da4`.

Two consequences follow.

1. The repository at HEAD is **internally contradictory in the authoring
   direction too**: the owning agent is told to author checked, the template it
   is told to use ships unchecked, and the terminal gate demands an artifact
   neither mentions. The stale-documentation defect is therefore not one-sided
   drift toward the old contract — it is drift in both directions from a change
   that touched only the executable surfaces.
2. The narrower reading is correct. The fabrication vector was the
   **composition**, and specifically the leg that made the checked state
   *mandatory at lint time*. Remove that leg and the checked default is a
   contract decision rather than a mechanically-forced fact. This is the
   evidentiary basis for D-2, and it materially changes Scope 2: the two
   surfaces above need **no change at all**, because opt-out is what they
   already describe.

Neither surface is in `state.json.allowedPaths`, and neither needs to be —
confirmed by reading them rather than by assuming.

All five decisions are closed by `bubbles.design`. D-1 and D-5 were reconciled

### D-1 — Migration posture for existing artifacts — **CLOSED: classify by authoring-contract epoch, never by cutover alone**

**Ruling.** The framework ships no migration script and performs no bulk
checkbox mutation. Legacy handling depends on the contract that scaffolded the
checklist. The delivering commit alone cannot classify every older file as
unchecked.

### D-1.1 Legacy classification contract

| Class | Provenance | Meaning of baseline bytes | Required handling |
|---|---|---|---|
| Current opt-out | The checklist was scaffolded from the BUG-037 template at or after the delivering commit. | Checked items are the current initial state. An unchecked item is a user rejection. | Apply AC-1 through AC-9 without migration. |
| Legacy pre-PD-12 checked | The checklist was scaffolded before `9e41da4` on 2026-08-17. | Checked items may be template-authored. They do not prove fresh human review. | Re-author the current checklist before review. Do not cite inherited checks as a human act. |
| Legacy PD-12 unchecked | The checklist was scaffolded at or after `9e41da4` and before the BUG-037 delivering commit. | Unchecked items may be template-authored. They are not automatically user rejections. | Re-author the current checklist before review only when history proves no user interaction occurred. |
| Legacy provenance unknown | History cannot establish the scaffold epoch or whether a user already interacted with the checklist. | Current checkbox bytes are ambiguous. | Fail closed. Keep the packet `in_progress` and do not mutate checkbox state until the artifact owner resolves provenance with the user. |

Current bytes never override provenance. A user may have changed either legacy
baseline after scaffolding. An unchecked row becomes protected user rejection
state as soon as user interaction may have occurred.

**Recorded population.** The design-time inventory contained both legacy
baseline shapes. This is the evidence that invalidates one pre-cutover bucket:

| File | checked | unchecked | first added | recorded shape |
|---|---|---|---|---|
| `bugs/BUG-032-…/uservalidation.md` | 7 | 0 | 2026-08-16 | pre-PD-12, checked |
| `bugs/BUG-033-…/uservalidation.md` | 0 | 4 | 2026-08-17 | PD-12, unchecked |
| `bugs/BUG-035-…/uservalidation.md` | 0 | 12 | 2026-08-18 | PD-12, unchecked |
| `bugs/BUG-036-…/uservalidation.md` | 0 | 5 | 2026-08-18 | PD-12, unchecked |
| `bugs/BUG-037-…/uservalidation.md` | 0 | 6 | this packet | PD-12, unchecked |

`9e41da4` separates the two historical template contracts. The later BUG-037
delivering commit separates both legacy classes from the current opt-out
contract. A file date alone does not prove which contract last scaffolded its
checklist, so history must establish that fact.

### D-1.2 Migration safety rules

1. The packet's artifact owner re-authors a current checklist before human
  review when provenance makes that operation safe.
2. Automation never re-authors after a user may have reviewed the checklist.
3. Automation never re-checks a known user rejection.
4. Ambiguous provenance blocks migration instead of selecting a convenient
  checkbox meaning.
5. The framework never scans downstream repositories or rewrites their files.

These rules preserve opt-out semantics for current files. They also preserve
the user's authority over every rejection. Legacy uncertainty cannot silently
become either acceptance or rejection.

### D-1.3 Upgrade-note contract

The corrected upgrade note must name both legacy classes. It must explain that
pre-PD-12 files may carry template-authored checks. It must explain that PD-12
files may carry template-authored unchecks. It must forbid inferring review or
rejection from either baseline.

The note must require provenance review before re-authoring. It must keep an
ambiguous packet `in_progress`. It must also state that no bulk migration
script exists or will ship.

**Rejected alternative.** A migration script cannot distinguish a
template-authored uncheck from a user's deliberate uncheck. Operator invocation
does not change that limitation. A script could erase the only rejection signal
the contract preserves.

**Planning consequence.** `bubbles.plan` must reconcile the D-1 scope text and
tests with these four classes. The plan must require `bubbles.docs` to replace
the current one-bucket upgrade note without editing any legacy acceptance file.

### D-2 — Does `artifact-lint.sh` re-acquire a checked requirement? — **CLOSED: NO. Lint stays shape-only.**

**Ruling.** `artifact-lint.sh` does **not** restore a "must carry at least one
checked `[x]`" check. Its checklist rules are unchanged. The only edit to that
file is the stale comment block at lines ~555-563, which explains a rationale
that no longer holds. The mechanical backstop the old rule provided moves to a
**template↔registry agreement check** (S2-T2).

**Rationale — three grounds, all verified.**

1. **Lint runs during planning, and the all-unchecked state is legitimate
   there.** A packet mid-review can legitimately have a user unchecking items,
   up to and including all of them. A lint that demands at least one `[x]`
   refuses the user's own act of rejecting everything. AC-4 exists to surface
   that state at the terminal transition, which is where it means something —
   not to make it un-lintable while the user is still working.

2. **The duplicate buys nothing.** Gate G136 already enforces *all* items
   checked at terminal. That is strictly stronger than "at least one checked".
   There is no input the lint rule would catch that G136 does not already
   refuse at the moment the claim stops being provisional. The rule would add
   planning friction and zero assurance.

3. **It is the coupling leg, and restoring it restores the vector.** This is the
   decisive ground. The ≥1-checked lint rule is precisely what *forced* the
   template to ship checked, and the composition "lint demands checked → template
   ships checked → terminal gate reads checked as sign-off" is the fabrication
   vector PD-12 correctly diagnosed. Under the new model the checked state comes
   from a **contract** — `acceptance-checklist.shippedState: checked` in
   `acceptance-authority.yaml`, a recorded owner decision. Deriving the checked
   state from a declared contract is sound. Deriving it from a *lint refusal*
   re-creates a chain in which three independent rules jointly assert that a
   human acted, with no rule actually checking that a human did. Keep the
   contract; do not rebuild the coupling.

The prompt asked that a restoration be justified explicitly. This ruling
declines to restore, so no such justification is owed — which is the cleaner
outcome and the reason the narrower root cause in § 1.3 matters.

**What replaces the backstop.** The only thing the old rule actually bought was
detection of a template authored in the wrong state. **S2-T2** buys exactly that
and nothing more: it asserts the uservalidation template block in
`feature-templates.md` agrees with `acceptance-authority.yaml`'s section
headings **and** its `shippedState`. That refuses a wrongly-authored template
without ever refusing a legitimately all-unchecked user file — the precise
separation the old rule could not make.

**Consequence for the scope list.** Scope 2 step 2 becomes "comment-only edit;
no rule change". SCN-B037-007 stands as written and is now an assertion that
HEAD behavior is *retained*, not changed. **S2-T2 is upgraded from a
nice-to-have to a load-bearing test** and gains an adversarial partner **S2-T9**
(a fixture template whose block ships unchecked must FAIL S2-T2). Scope 2 DoD
updated: the D-2 item now reads as a retention-plus-comment obligation.

### D-3 — G057 and the `bubbles.journey` "never auto-checks" rule — **CLOSED: three-way split; the permission and the prohibition belong to DIFFERENT agents; G057's clause is narrowed and declared advisory**

**The three-way split, as required.**

| Act | Verdict | Mechanically enforceable? |
|---|---|---|
| Automation authors the **initial** checked state when the artifact is created | **PERMITTED**, and required by AC-1 | **Yes** — via the template↔registry check (S2-T2). |
| Automation **re-checks** an item the user unchecked | **FORBIDDEN** (AC-6) | **No.** Advisory agent-instruction only. |
| Automation **toggles** an item either way to mirror a test outcome | **FORBIDDEN** | **No.** Advisory agent-instruction only. |

**The honest statement about mechanism.** No file-level mechanism can
distinguish rows 1 and 2. Both produce a byte-identical `- [x]`, and
`uservalidation.md` carries no authorship or history of its own. Git history
cannot close the gap either: it distinguishes them only when the user's uncheck
was itself committed, and an agent that overwrites an *uncommitted* uncheck
leaves no trace anywhere. Rows 2 and 3 are therefore obligations on agent
behavior, enforced by instruction and by review, **not by a guard**. This is
recorded here rather than papered over with a rule no mechanism enforces.

**A verified fact that resolves most of the apparent conflict.** G057's sole
enforcer is `bubbles/scripts/guards/control-plane-checks.sh`, and that script
**never reads `uservalidation.md` at all** — zero occurrences. So the clause
"`uservalidation.md` … MUST NOT be toggled to mirror automation outcomes" is
*already* advisory prose sitting inside a gate description whose enforcer does
not implement it. Declaring it advisory is not a weakening; it is a correction
of a description that overstates what the gate does, which is exactly the class
of defect GC-2 and GC-3 exist to fix.

**The tension dissolves on agent ownership.** The permitted act and the
forbidden act belong to different agents, at different times:

- **`bubbles.plan`** authors `uservalidation.md` at packet creation. It has the
  AC-1 permission — and its instruction at `agents/bubbles.plan.agent.md:230`
  already says "Create with checked-by-default baseline template (`- [x]`
  items)". **No change to that agent is required.**
- **`bubbles.journey`** runs later, against a live product, on a file that
  already exists. It never has a legitimate reason to write a `[x]`. Its
  prohibition therefore stays **absolute and unqualified**, with no exception
  carved out of it.

That is the clean resolution: the exception the bug packet feared would have to
be added to the journey rule does not exist, because journey is never the
author.

**Rulings.**

- **`gates.yaml` G057.description** — amend. Replace the single clause with all
  three rows above, and state plainly that only the first is mechanically
  checked while the other two are agent-instruction obligations that this gate's
  enforcer does not verify. Keep the mirroring prohibition verbatim in substance.
- **`feature-templates.md` `bubbles.journey` rule** — keep in force. Restate it
  so it names the split and cites the correct owner of the authoring permission,
  but do **not** add an auto-check exception to it. Its substance is unchanged.
- **`agents/bubbles.journey.agent.md`** — no change. Its lines 72 and 89 are
  correct as written and it is not in `allowedPaths`; none is needed.
- **`agents/bubbles.plan.agent.md`** — no change. Already correct; not in
  `allowedPaths`; none is needed.

**Consequence for the scope list.** Scope 2 step 1's journey sub-bullet
simplifies to "restate, do not except". Scope 4 step 2 changes from conditional
("amend per D-3 if that decision requires it") to **required, with specified
content**. Added: Scope 4 DoD item that G057's description declares the advisory
status of rows 2 and 3 explicitly, and test **S4-T8** asserting G057's
description contains no claim its enforcer does not implement.

### D-5 — Failure-code naming and lifecycle — **CLOSED: keep the `PD12-*` prefix and declare every supported emission**

**Ruling.** No code is retired while a supported registry state can emit it.
The canonical `failureCodes` set declares every code the library can emit under
any supported configuration. The set is not limited to codes reachable under
the shipped default values.

`PD12-NO-RECORD` is conditionally active. The shipped
`requiredAtTerminal: false` value leaves it dormant. An explicit downstream
`requiredAtTerminal: true` value activates it and preserves the compliance
override without a library fork.

### D-5.1 Failure-code lifecycle

| Lifecycle | Contract | BUG-037 classification |
|---|---|---|
| Default-active | Declared in `failureCodes` and reachable for an invalid artifact under the shipped registry. | The six existing checklist, readiness, and present-record shape codes. |
| Conditional-active | Declared in `failureCodes` and reachable only when an explicit supported registry value enables its condition. | `PD12-NO-RECORD`, activated only by `acceptance-record.requiredAtTerminal: true`. |
| Bootstrap-active | Declared in the canonical registry but emitted without depending on a successful registry read. | `PD12-AUTHORITY-UNAVAILABLE`, required when the registry or a required contract field cannot be resolved. |
| Retired | Unreachable under every supported registry state and absent from production emitters and active declarations. Historical prose may still name it. | None in this remediation. |

A lifecycle transition is a contract change. Retirement requires removal of
the source emitter and every supported activation path in the same change.
Changing only the shipped default never retires a conditional code.

### D-5.2 Fail-closed authority reads

The reader must resolve the registry path and every required field before it
can return acceptance. A missing, unreadable, or malformed authority produces
`PD12-AUTHORITY-UNAVAILABLE` and a non-zero verdict. The bootstrap code must not
depend on parsing the unavailable authority before it can be emitted.

`requiredAtTerminal` accepts only the exact values `true` and `false`. A missing
or different value is an authority failure. It must never degrade to the
shipped `false` posture.

This failure path does not change the opt-out default. A valid shipped registry
still accepts a fully checked record-less checklist. A valid downstream
registry may still require an authored record explicitly.

### D-5.3 Closure checks

The closure check must compare source emitters with canonical declarations in
both directions. It must not exempt an undeclared source literal. Every
declared code must also have an executed fixture that reaches its lifecycle
class.

The required matrix includes these cases:

1. The shipped `false` value emits no `PD12-NO-RECORD` finding.
2. A fixture `true` override emits declared `PD12-NO-RECORD`.
3. Missing and malformed authorities emit declared
   `PD12-AUTHORITY-UNAVAILABLE` and return non-zero.
4. Every source-emittable code appears in `failureCodes`.
5. Every code in `failureCodes` is reachable by a default, conditional, or
   bootstrap fixture.

**Current discrepancy.** The library retains the conditional
`PD12-NO-RECORD` emitter. S1-T8 executes it under a `true` override. The registry
does not declare it, and S1-T10c treats that mismatch as a special case. This
design rejects that special case. Source, registry, documentation, and tests
must adopt the lifecycle contract together.

**Rationale.** Removing the emitter would break the documented downstream
override. Keeping an undeclared emitter would break the registry's closed-set
claim. Declaring the conditional code preserves both contracts without
weakening user rejection authority.

The `PD12-*` prefix remains historical and stable. The library and registry
ship downstream, and guard output enters archived evidence. Renaming the prefix
would orphan consumers without changing behavior.

**Planning consequence.** `bubbles.plan` must reconcile Scope 1, S1-T8,
S1-T10, and every retirement assertion. It must add fail-closed authority cases
for `F-B037-GAPS-FAILCLOSED`. Later owners must update source, registry,
documentation, and persistent tests as one contract change.

## 3.6 What the owner's model gives up

Recorded plainly, per the constraint that the cost be stated rather than
papered over. [spec.md](spec.md) § 5 records the decision; this section records
its **design-level** consequence.

**A checked box is no longer evidence that a human acted.** After this fix, Gate
G136 at a terminal transition proves exactly one thing: *no user recorded an
objection in this file*. That state is reached identically by "the user
reviewed the behavior and was satisfied" and by "nobody ever opened the file".
The gate cannot separate them, and nothing downstream of it can either.

**G136's role narrows from acceptance proof to rejection channel.** Before this
fix it attempted to assert that acceptance happened. After it, it asserts only
that rejection did not. That is a real reduction in assurance and it is the
price of the owner's requirement — a satisfied user performing zero acts is
incompatible with any proof that the user acted, by construction.

**BUG-032 is the concrete demonstration, not a hypothetical.** Its seven boxes
were authored on 2026-08-16 by the pre-PD-12 template. After this fix that file
satisfies the terminal gate. Nothing in the repository can tell it apart from a
file a human reviewed item by item. That is why D-4's note says so explicitly.

**What is NOT given up, and must not be weakened later:**

| Property | Preserved by |
|---|---|
| An unchecked item still refuses a terminal transition, and every one is named | AC-4; the BUG-029 closure shape is proven intact by S1-T3 and S3-T3 |
| The guard never edits the artifact | AC-5; proven by sha256 comparison in S3-T4 |
| An agent can never name itself acceptor when a record is present | AC-8; `^bubbles\.` prohibition retained, proven by S1-T4 |
| Automation readiness grants no acceptance | AC-9; proven by S1-T7 |
| A user's uncheck is never reversed by automation | AC-6; **advisory only** — see D-3's honest statement |

The last row is the only one with no mechanism behind it. It is listed here
rather than omitted, because a preserved property with no enforcement is a
different kind of claim from one with a test, and conflating the two would be
the same failure this bug is about.

## 4. Fix approach

Four sequential scopes, each independently testable. See
[scopes.md](scopes.md).

1. **Scope 1 — invert the contract and the shared reader.** The registry and
   `acceptance-authority-lib.sh` are the single authority; everything else
   reads them. Changing them first means every later scope is verifying against
   an already-correct source of truth.
2. **Scope 2 — template, lint, and authoring agents.** What gets written.
3. **Scope 3 — guard and regression surfaces.** What gets enforced, with the
   BUG-029 pin explicitly preserved and proven.
4. **Scope 4 — governance documentation and generated artifacts.** What gets
   described, including the four stale surfaces and the changelog.

Scope 1 must land before Scope 3, because Check 43 and the regression tests both
source the library that Scope 1 changes.
